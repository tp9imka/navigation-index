**MINS: Efficient and Robust Multisensor-aided Inertial Navigation System** - Lee, Geneva, Chen, Huang (Univ. of Delaware RPNG), arXiv 2309.15390, 2023. [paper](https://arxiv.org/abs/2309.15390) | [code](https://github.com/rpng/MINS) | Read: full text, arXiv HTML v1 (main body and results; tail of appendices not read)

## Problem
Fusing many sensors on a vehicle runs into asynchronous/delayed measurements, compute that grows with sensor count, and drifting offline calibration. Initialization is also hard under constrained (ground vehicle) motion. MINS targets one filter that takes any subset of camera, LiDAR, wheel and GNSS on top of an IMU.

## Method
- MSCKF-style EKF built on the OpenVINS lineage. State = current IMU state + window of historical IMU pose clones.
- Sensors: arbitrary number of cameras (MSCKF update with nullspace projection), wheel encoders (2D odometry integrated between IMU times, relative-pose update), LiDARs (direct point-to-plane against a local ikd-tree map, no feature extraction), GNSS (position in local ENU; general global pose measurements also supported).
- Online spatial and temporal calibration of all sensors; only parameters flagged as inaccurate go into the state, to save compute.
- On-manifold polynomial interpolation between clones lets asynchronous sensors update without a clone at every measurement time; interpolation error is modelled as Gaussian noise (Eq. 60).
- Dynamic cloning: picks the lowest clone rate that keeps interpolation error under a threshold (Eq. 61) => more clones in aggressive motion, fewer in slow motion. Defaults: 3rd-order polynomial, 20 Hz cloning (Sec. 4.1).
- IMU-wheel dynamic initialization (no exteroceptive sensor needed); runs in a local frame until GNSS is available, then switches to a global frame.

## Data and sensors
- IMU + any of: camera(s), LiDAR(s), wheel encoders, GNSS.
- Simulation on EuRoC-derived and synthetic UD trajectories.
- Real: [KAIST Urban / Complex Urban](../dataset-cards/complex-urban.md) sequences 18-39 (includes highway), UD Husky (indoor, outdoor, trail; own dataset).

## Headline results (as reported)
- Table 3 (sim, EuRoC V2_02 trajectory, 10 runs): without the interpolation-error model position NEES reaches 3e3 at 4 Hz cloning; with it, NEES stays below 4 at all rates (4 Hz: 0.550 deg / 0.061 m).
- Table 4 (dynamic cloning): fixed 30 Hz cloning 80.5 s, 0.178 deg / 0.019 m; dynamic cloning (coefficient 1) ~62% of the time at 0.218 deg / 0.028 m.
- Fig. 9 (UD Warehouse sim, each sensor dropped for 5 s): two-sensor systems keep the error gained during the outage (except IMU-GNSS, which recovers); systems with more than two sensors bound the error growth.
- Table 6 (KAIST Urban, avg 5 runs, position ATE in m per 1 km; >30 m not reported): urban38 / urban39 - MINS(I,C,L,W,G) 0.64 / 0.56; MINS(I,L,W) 3.24 / 2.50; FAST-LIO2 4.74 / 1.64. Per text, camera-only methods failed to initialize on highways; FAST-LIO2 and MINS(I,L) mostly failed on highways, MINS(I,L,W) ran consistently thanks to wheel initialization.
- Table 7 (UD Husky, ATE m): MINS(I,L) 0.07 / 0.11 on indoor I1 / I2; all-sensor MINS row reads 0.96 to 3.03 m across sequences (exact column mapping not located in our extract).
- Table 8 (timing, KAIST urban38, ThinkPad P17 i7, 32 GB, ms total): FAST-LIO2 20; MINS(I,L) 28; MINS(I,C) 54; MINS(I,C,L,W,G) 47; VINS-Fusion 95; ORB-SLAM3 328. Text: the EKF update itself is ~1 ms regardless of sensor count.

## Limitations
- Stated by authors: GNSS-to-local alignment from a short trajectory with noisy single-point GPS can be poor; wheel model handles sharp turns badly and hurt indoor Husky results; adding all sensors did not always give the best result (trails). Future work: optimal weighting of multi-modal measurements.
- Our read: arXiv preprint as read (no journal-ref on arXiv). GNSS is fused as position only (no raw pseudoranges), so it does not itself detect spoofing; a spoofed fix would be accepted unless gated. Ground-vehicle focus; no aerial results.

## Reproduction effort (estimate)
Estimate:
- Hardware: x86 laptop; Table 8 shows <60 ms per step for all MINS configs on a laptop i7.
- Data: simulator needs nothing; KAIST bags are large (tens of GB per sequence) and need the registration/conversion step or the HF mirror.
- Time-to-first-result: ~half a day for build + simulation run; ~1 day for one KAIST sequence end to end.
- Not reproducible quickly: UD Husky dataset availability not checked; full 22-sequence Table 6 is days of runtime.

## What a hackathon team can take from it
- The closest thing to a ready "assured PNT" estimator: run with GNSS, cut GNSS mid-run, show the IMU+camera/LiDAR/wheel solution holding. See [integration card](../integration-cards/rpng__mins.md).
- Fig. 9 protocol (drop each sensor for 5 s, plot error before/after) is a cheap, convincing demo and evaluation format for GNSS-denied resilience.
- Wheel-aided initialization fixes the "VIO will not initialize on a car" problem; copy the idea for any ground platform.
- Interpolation-with-modelled-error is the trick for fusing asynchronous sensors without a clone per measurement.
- Check (and if needed add) a chi-square gate on the GNSS update before demoing spoofing scenarios; we did not see GNSS outlier handling evaluated in the parts we read. Base layer is [OpenVINS](openvins-2020.md).
